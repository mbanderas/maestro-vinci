# Design Guide

A practical reference for producing high-fidelity design work, interactive prototypes, and design-system–driven UI. Written as a working manual — read it cover to cover once, then dip in by topic.

---

## How to use this guide

Each chapter is self-contained but they reinforce each other. If you only have time for three things, read:

1. **[01 — Design Process](./01-design-process.md)** — the workflow that makes everything else possible
2. **[03 — Hi-Fi Design Principles](./03-hi-fi-design.md)** — the bar to clear
3. **[18 — Common Pitfalls](./18-common-pitfalls.md)** — the mistakes that mark work as "generated" instead of "designed"

After that, jump to the topic you're working in.

## Core beliefs

A handful of principles underpin everything in this guide. If you remember nothing else:

1. **Context beats invention.** Start from real material — a system, a brand, a codebase, a reference. Pure invention almost always produces generic work.
2. **Constraints make work better.** A locked palette, a fixed grid, a defined type scale — these accelerate decisions and raise the floor.
3. **Specificity sells fidelity.** Real copy, real numbers, real images. Lorem ipsum and "Headline goes here" reveal a half-finished design.
4. **Restraint is the move.** One accent color used confidently. One typeface used across a scale. One motion language. The temptation is always to add more.
5. **Show the work early.** A rough scaffold reviewed at 30% beats a polished file reviewed at 90%. Iteration is cheaper than rework.
6. **Variations should be comparable.** Place options side by side. Don't ship variations as separate files the reviewer has to mentally A/B.
7. **Every element earns its place.** If you can't say why something is there, take it out.

## Conventions in this guide

- **Code samples** are illustrative — adapt to whatever stack you're working in.
- **Numerical recommendations** (sizes, spacing, contrast ratios) are starting points, not laws. Defend deviations; don't drift into them.
- **"You"** means the designer doing the work. **"The user"** or **"the reviewer"** means the person you're designing for or with.
- Where a section gives a list of options or trade-offs, the order is usually intentional — earlier items are the more common right answer.

---

*This guide describes an approach, not a rulebook. Every project has its own gravity. Adapt the principles; don't apply them mechanically.*
